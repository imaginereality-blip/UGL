UI Audit Avalonia · AXAML Controller-First

Five interface upgrades for a cleaner, more professional UGL

UGL's controller-first shell — five full-height cards, a bottom hint bar, an overlay-based Settings screen — is already the right structure for a cabinet dashboard. What's holding it back from reading as premium is inconsistency: magic-number overlay colors scattered across views, a hint bar written as one run-on sentence, flat accent-fill selections, and emoji standing in for icons. Below are five concrete, low-risk changes, each shown before/after against the app's own dark theme — none require new dependencies, none touch the controller-input or MVVM architecture.

Constraints respected
— Pure AXAML + DynamicResource theme keys, no CSS
— 1920×1080, fixed full-screen, no window chrome
— Cards stay text/gradient-free on the face (§6.1 spec)
— No hover states — gamepad/D-pad focus only
— Selection driven from code-behind, not Avalonia's focus system
— Zero new NuGet packages or fonts
01

Consolidate the magic-number overlays into theme tokens

Quick win

ConfigEditorView, FilterOverlayView and MainWindow each hand-roll their own translucent grays — #22FFFFFF, #33FFFFFF, #44FFFFFF, #66FFFFFF, #88FFFFFF, #CC000000, #EE0D0D1A, #F00D0D1A — eight near-identical grays with no shared name. ThemeKeys.OverlayBg already exists in AvaloniaThemeService and is never referenced. Add Divider, ScrimHeavy and PanelBackground alongside it and point every one of those literals at a token — same pixels today, themeable and consistent from here on.

02

Wire up CardSpacing; soften the selection border into a glow

Quick win

ThemeKeys.CardSpacing is defined and populated by AvaloniaThemeService, but CategoryCard/GameCard hardcode Margin="2" instead of binding to it — the token is dead. Bind it, and cards get real, theme-driven breathing room. Separately, the selection highlight is a single flat-color border — bold, but hard, almost like an old browser input outline. A Border.Effect with a soft DropShadowEffect in the highlight color (kept alongside the existing border, not replacing it) reads as a glow the card is lit by, not a rectangle drawn on top — same configurable color/pulse from CardHighlightSettings, no new settings UI needed. The card face itself stays exactly as spec'd — art only, no text, no scale-up.

After — CardSpacing token, glow
03

Turn the hint bar into scannable button chips

Medium effort

Every hint bar (HomeMenuView, GameBrowserView, ConfigEditorView, FilterOverlayView) is one long TextBlock string — "A Launch     B Back     ← → Browse…" — read from a couch, at a glance, while holding a controller. A small reusable ButtonHint UserControl (round badge for the glyph + label, bound to a lightweight ButtonHintViewModel list) turns that string into discrete chips laid out in a StackPanel — same data, same font tokens, dramatically easier to scan. This is the one change here worth a small new control, since the pattern repeats on four screens.

06

Swap emoji glyphs for Segoe Fluent Icons

Quick win

"⚙ Settings", "✕ Close" and the "★" favorite badge are literal emoji characters — they render in Windows' colorful emoji font, at inconsistent weight and baseline versus the surrounding UI text, and look noticeably different across Windows versions. Segoe Fluent Icons ships with Windows 10/11 already (it's the same font File Explorer and Settings use for their glyphs) — setting FontFamily="Segoe Fluent Icons" on those specific TextBlocks and swapping the character to the matching Fluent codepoint costs nothing new and instantly reads as native, monochrome, on-brand chrome instead of borrowed emoji.

Settings menu deep-dive

The Settings screen itself has the most room to improve

Reading GamesConfigView, ThemeConfigView and their siblings closely, the tab content is where UGL reads least "premium" — long flat forms, help text baked into field labels, a broken Theme picker, and status colors that don't match anything else in the app. Four more fixes, same rules: AXAML/DynamicResource only, no new dependencies.

07

Group the Games editor into labeled sections

Medium effort

The Games → Settings tab is one flat StackPanel of roughly fifteen field groups — Title, System, Categories, Emulator, Genre, Players, ROM Path, Process Override, Bezel, DemulShooter, Display Mode, BIOS Override, Disabled Peripherals, Player Device Assignments — with no visual separation between "things every game needs" and "rare per-game overrides." A few .hr-style divider Borders plus small uppercase section captions (Identity / Launch / Display & Input — same idea already used to separate the hint bar from content) turn it from a wall of fields into a form you can scan.

08

Pull controller-hint text out of the field labels

Quick win

Labels like "System * (controller: Left/Right)" and "BIOS Override (optional — only if this game needs different BIOS file(s)…; A to enter, Up/Down to move, A to remove, B to exit)" pack the field name, its requirement state, a usage caveat, and the full control scheme into one wrapped sentence. The control scheme is static per-widget-type (every ComboBox is always Left/Right, every reorderable list is always A/Up-Down/A/B) — it belongs once in the shared bottom hint bar bound to whatever field currently has focus, not repeated and re-typed on every field. Labels shrink to just the name and its requirement/caveat.

09

Fix the Theme tab's duplicate, non-functional picker

Medium effort

ThemeConfigView renders two selectors for the same choice: a row of 200×140 "swatch cards" whose three color dots are hardcoded literals (#FF0078D4/#FF1A1A2E/#FF16213E) identical on every card regardless of theme, followed by a plain ListBox commented "more reliable for now" — which is the control that actually drives selection. That's a dead, misleading picker sitting above the real one. Bind each card's three dots to that theme's own AccentColor/BackgroundColor/ SurfaceColor and put the SelectedItem binding directly on the cards' container (a ListBox with a WrapPanel panel template can host exactly this card layout) — one control, doing what it visually promises.

10

Give status/destructive colors the same token treatment

Quick win

Validation errors are #FFFF4444, save-success status is #FF44FF88, the Delete button's label is plain white text — three more hardcoded literals repeated across every config tab, and none related to the app's actual accent. Add Success and Danger to ThemeKeys next to Accent, and reuse the quitRow red already defined in ConfigEditorView.Styles for every Delete button — it's currently only applied to the Settings sidebar's Quit row, despite Games/Systems/Categories all having their own Delete actions in plain button styling today.

Collapse the Paths tab's five repeated field blocks into a table

Medium effort

PathsConfigView repeats the same tall block — name, two lines of description, a text field, a Browse button — five times in a row for Media/ROMs/Emulators/Addons/Logs Root, pushing "Save Paths" and the whole Per-System section below the fold. Make the Card Highlight preview an actual card, not a labeled box

Quick win

CardHighlightConfigView's "Preview" is a plain SurfaceColor box with the word "Preview" centered in it and the chosen border applied around the whole box — closer to a debug swatch than a preview of what a selected card actually looks like. Since this tab exists specifically to tune how the selection reads on real cards, drop a placeholder cover thumbnail (reuse CategoryCard's own big-letter placeholder look) inside that box so the border/glow renders exactly as it will on Home Menu and Game Browser — while also being the one screen in this document where the recent art-direction call (recommendation 02, glow instead of hard line) should land first, since users tune it here before ever seeing it in play.

13

Collapse the sidebar on explicit enter, not on arrow-move

Medium effort

The 240px sidebar ListBox currently switches tab content live as ↑↓ moves the highlight — useful for quickly previewing what's in each tab, but it means the sidebar can't simply auto-hide on selection without hiding/reappearing on every arrow press while browsing. Keep that live-preview behavior for ↑↓, and add a second, explicit state: pressing A "enters" the highlighted tab — same commit gesture GamesConfigViewModel.IsEditorOpen already uses to hide its own game list — collapsing the sidebar and giving the content the full width. B returns to the sidebar exactly like Cancel already does for the game editor. One new bool per ConfigEditorViewModel (IsSidebarCollapsed), no change to the live-preview browsing people already rely on.

14

Group the 11-row sidebar into labeled clusters

Quick win

ConfigEditorViewModel.MenuItems is one flat list — Categories, Games, Systems, Audio, Theme, Card Highlight, Paths, Controllers, Output Hooks, Updates, Scraper, Quit — mixing content (what's in the library), appearance (how it looks) and infrastructure (where things live, what's plugged in) with no visual separation. A SettingsMenuItem already carries just Label/Tab/IsQuit — add an optional non-selectable SettingsMenuItem header row (its own DataTemplate, skipped by NavigateMenuUp/Down) between three groups: Content (Categories, Games, Systems), Appearance (Theme, Card Highlight), System (Audio, Paths, Controllers, Output Hooks, Updates, Scraper). Same ordering, same rows, just labeled — and it gives future tabs an obvious place to land.

15

Make the Systems tab's inner sub-tabs match Audio/Games

Quick win

Three tabs have an LB/RB-switchable inner tab bar — Games (Settings/Art), Audio (Music/System Sounds), Systems (Systems/Emulators). Games and Audio wrap each button in Classes="cfgField" Classes.fieldFocused="…" so the currently-focused sub-tab gets the accent border everyone learns to look for; SystemsConfigView's two buttons (SystemsTabBtn/EmulatorsTabBtn) are plain Buttons with no focus wrapper at all — the one place in Settings where LB/RB switching gives no visual feedback that it did anything. Wrapping them the same way is a one-file fix and removes the one inconsistent corner of an otherwise-uniform pattern.
